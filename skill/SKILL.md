# Problem Finder

Use this skill when a startup idea, hackathon idea, or "what should I build" request needs a real problem before anyone starts solutioning.

Builders are good at solutioning, not probleming. Obvious, visible, razor-thin problems feel safe. They are not. A solution already on the table is a clue about a suspected problem, not permission to skip discovery.

## Intake

Capture these before scoring:

- Original framing, exactly as received
- Who the user thinks the customer is
- Whether a solution is already implied
- Decision this informs (build, skip, sharpen, demo)
- Expected output

If a field is blank and cannot be safely inferred, ask or state the assumption.

## Core Workflow

1. Preserve the messy original framing.
2. Restate the job from the person doing the work.
3. List current workarounds. No workaround means the problem is suspect.
4. Score fragmentation, incentive misalignment, incumbent neglect, and cost bearer.
5. Reject obvious, feel-safe framings.
6. Output 2-3 ranked one-sentence problems, each naming worker, workaround, and structural gap.
7. Only then, if asked what to build, stay inside the #1 symptom.

## Boundaries

- Do not suggest a product, feature, app, or stack before the report exists.
- Do not talk to the software buyer when the pain sits with the person doing the job.
- Do not accept the first framing.
- Do not re-bundle rejected framings after sharpening.
